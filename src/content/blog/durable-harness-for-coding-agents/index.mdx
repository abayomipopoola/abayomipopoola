Every team has its own idea of how work should get done. Product wants tickets triaged. Engineering wants predictable changes with tests. Business logic needs to be deterministic. When you bring a coding agent into that workflow, you want to ship fast, but you also need the model to stay grounded. Nobody wants an agent that invents a new checkout flow because it sounded clever.

### The Model Asks. The Harness Answers.

An AI coding agent is a model in a loop. It reads a task, asks for a tool, reads what came back, and goes round again until the work is done. Every time it asks for a tool, it asks to act on your machine: read a file, run a command, edit a module, or touch credentials.

Something has to answer that request. That something is the harness: the deterministic code around the model that runs the loop, guards every tool call, and decides what counts as done.

<HarnessLoop />

Look at what the model actually owns in that drawing: two boxes out of five. Every other box is code. If the harness doesn’t enforce those boundaries in code, the model ends up answering its own requests, putting the very thing you meant to check in charge of the check.

As much as I use Codex and Claude Code, I found myself drawn to Pi's approach: a minimal harness, with control over my machine, permissions and context. I liked that simplicity, but I also needed memory, a shared code index and somewhere for the rest of the team to work with the agent.

So I kept building small tools. A model router to use different models inside Pi, Codex or Claude Code. Orchestration to make agents plan before implementing. Scripts to stop context compaction from summarising away the important details of a long task.

Those tools became [mux](https://usemux.com/), a durable harness for coding agents, available today in preview.

There are two parts: **[muxcode](https://muxco.de/)**, the free agent harness that runs on your Mac, and **[mux](https://usemux.com/)**, the cloud index, memory, and sandbox behind it.

### muxcode Is the Agent Harness

Your agent runs on your machine. [muxco.de](https://muxco.de/) enforces scope, permissions and workflow gates locally.

Under the hood, muxcode is a native Mac app built in two halves: a Rust host that owns your sessions, permission gate, and workflow engine, paired with a React window for the composer, transcript, and settings. It bundles `pi`, an open-source coding agent harness, built from source so nothing needs to sit on your `PATH`, and drives one `pi` process per task over RPC.

Every tool call the agent proposes passes through the gate in the Rust host before it can touch your machine:

- **Plan mode refuses writes without a card.** Plan mode is strictly for research and proposals, so any attempt to edit a file or run a mutating command is refused immediately and explained to the agent.
- **Project fences and `.git` guards.** Edits outside the project root, or inside `.git`, which controls what hooks and programs Git executes, always ask first.
- **Explicit permission cards.** When a call needs approval, muxcode names the exact command or path and gives you four choices: _allow once_, _allow for this session_, _always allow_ (which saves a durable rule you keep), or _deny_.

#### Fresh Context Windows by Default: No Compaction

When a long task nears the context limit, muxcode opens a fresh context window by default rather than compacting the conversation. Durable notes carry over, and the agent can search the full session history to recover the details it needs.

Standard summary compaction has two failure modes on long engineering tasks: it spends a full, uncached model call just to write a summary (up to \$3.80 on Claude Opus 5.5 or \$9.50 on Claude Fable 5.1 before output tokens), and whatever file paths, invariants, or edge cases the summary drops are gone from the model's view forever.

When the window rolls over, no model writes a summary. Instead, the new window starts with the system prompt, tools, and a deterministic handoff (capped at `4,000` characters per record and `20,000` characters total) that quotes your requests, latest answer, active note revisions, and trailing tool results. Everything else stays on disk in append-only session history and versioned task notes that the agent can page back (up to `40,000` characters per read) whenever it needs exact detail.

#### Bring the Plans You Already Pay For

It also works with the plans you already pay for: Claude Code, Codex CLI, Grok CLI, Cursor, Antigravity and OpenRouter. muxcode orchestrates them; you keep your subscriptions.

muxcode serves no hosted chat models of its own. Every role in your workflow is filled from the model sign-ins you already have on your Mac, and you can swap a seat's model or reasoning level at any time without losing your worktree, session history, or permission rules.

#### Plan-First Orchestration, Sized by Clef

Not every change needs the whole pipeline. A one-line fix that your test suite already covers shouldn't wait on a plan, a review and a judge. So before any work starts, muxcode decides how much process the change deserves: a small change your checks can prove goes straight to a single worker, anything else gets the full plan-first workflow, and a change where a mistake could slip past the tests also gets a second reviewer on a different model.

When a change takes the workflow, it plans first, builds second, and proves the change in code before any model is allowed to judge it:

1. **Root (`GPT-6 Luna`)** starts the run from your prompt.
2. **Plan & Self-Review (`Architect · Claude Opus 5.5 @ high`)** writes one to four contracts, naming the exact goal, route kind (`logic`, `ui`, or `terminal`), allowed file paths, frozen paths it must not touch, and verification commands, and re-reads its own plan in a fresh session.
3. **Pre-Worker Screens & Baseline** run in host code before any file is edited: a mechanical check ensures backticked verification commands actually run and cannot trivially pass (like `npm test || true`), a Clef contract screen (at `0.7` confidence) checks for missing checks or scope gaps, static lint verifies referenced tools and directories exist, and the host records a baseline of up to 10 read-only project checks on the untouched tree.
4. **Worker (`Opus 5.5 @ medium`)** implements the contract while the host runs per-file checks after edits and watches for repeated command failures or drift.
5. **The Gate (host code, zero tokens)** checks the finished attempt before any judge sees it: out-of-scope edits pause the run, touched frozen paths stop it, verification commands must exit `0`, secret scans block newly added keys, and project checks are compared against the baseline.
6. **Judge (`GPT-6.1 Sol @ high · four lenses`) & Retry (`Claude Fable 5.1 @ xhigh`)**: Only after the deterministic gate passes does the judge, always on a model that neither planned nor wrote the change, read it across four lenses: _contract_, _tests_, _scope_, and _your words_. If a check fails or the Judge rejects the diff, the route goes once to a second model (`Fable 5.1`) and must pass the same gate again. Every run is bounded by hard ceilings: `500,000` tokens, `60` minutes of active time, or `40` attempts.

That decision is made by **Clef**, Cloudflare's decision model. Rather than paying a chat model to write commentary at every step, muxcode asks Clef short, typed questions: can this project's checks prove the change, is it confined to one place, could a wrong version pass the tests? Clef uses the same kind of question elsewhere too, to screen a plan before work starts, to tell whether a failing check is new, and to notice a worker going in circles.

What makes those answers trustworthy is that Clef returns a probability, not an opinion. muxcode only acts when that probability clears a bar set in code, and every bar is tested against real examples we labelled by hand. A chat model's "yes" carries no such number, so muxcode never acts on one. And where measuring showed Clef wasn't earning its keep, choosing reasoning levels and workers, we took that job away: every seat now runs at the model and level you choose.

Each change is read once, and only a confident answer takes it off the full workflow:

### mux Is the Cloud Sandbox Behind It

Instead of giving every tool its own view of the codebase, your workspace keeps one shared index of your team's repositories. Connect your GitHub repositories once, and authorised team members and agents can search that index from muxcode, cloud sandboxes or MCP clients. You can issue scoped keys, revoke access per member and re-index on push.

When you connect repositories to [usemux.com](https://usemux.com/), mux mirrors them into Cloudflare Artifacts and indexes them in one container per workspace (which sleeps after 3 idle minutes). When an agent calls `get_context`, mux returns a single ranked context packet (budgeted at `6,000` UTF-8 bytes by default, adjustable from `1,024` to `16,000` bytes) that combines:

- **Code passages** tied to the exact commit they were read at;
- **Two-hop code graph neighbours**: imports, tests, and cross-repository routes one service calls in another;
- **Owner-approved workspace findings**; and
- **Agent memory**, capped at one-third (`2,000` bytes) of the packet so unreviewed notes never crowd out the code itself.

#### Shared and Private Git-Backed Memory

An agent that starts every session from zero relearns the same lessons about how your team deploys, which integration test is flaky, and what conventions your repo expects. Each mux workspace gives your agents two tiers of durable Git-backed memory: one **shared repository** for the whole workspace, and one **private repository** per member.

Each memory repo starts at `MEMORY.md` (an `8 KiB` index map linking to `[[topic]]` files up to `64 KiB` each, up to `256` files / `2 MiB` per repo). Agents read, search, and save through a single tool, `workspace_memory`. Every write names the repo's current revision and a `mutationId`: if another agent committed in the meantime, mux returns `409 memory_conflict` with the new head so the agent can re-read and merge cleanly.

#### Pattern Search, Semantic Search, and Two-Sided MCP

Pattern search is included on every plan. Pro and Pro+ add semantic search, so you can ask questions like _"where do we validate checkout?"_ or _"what calls the billing webhook?"_ Results include the matching code, file, line numbers and commit.

Because mux exposes a hosted MCP server at `https://usemux.com/mcp`, your shared index and workspace memory aren't locked inside one app. A workspace owner can mint scoped `Bearer hk_live_…` keys so agents in Claude Code, Codex, or Copilot CLI can query the exact same codebase index and memory, while muxcode also lets local tasks on your Mac run your own MCP servers from `~/.muxcode/mcp.json`, gated per task and per tool call.

#### Cloud Sandboxes That Work While Your Laptop Sleeps

Cloud sandboxes let work continue while your laptop sleeps. Triage takes a bug report, investigates it in a clone of the project and leaves a branch you can review and land in muxcode.

Running an unattended agent on your laptop means every command it executes shares your SSH agent, environment variables, and local network. A mux cloud sandbox moves both the agent loop and its commands off your machine while keeping your long-lived credentials on your Mac:

Each cloud task is split into two isolated halves on Cloudflare:

- **The Task Durable Object** runs the agent loop (`pi-durable`), persists the conversation step by step so the run survives your laptop closing, and holds a short-lived sign-in loan from your Mac (an access token or 12-hour API key lease, never a refresh token).
- **The Linux Container (`standard-3`: 2 vCPU, 8 GiB RAM, 16 GB disk)** runs every command and file operation with full toolchains (Rust, Node, Go, Python, JDK, PHP), holds **zero Mac credentials**, and has only one way out to the network: the sandbox egress gateway.

As the task works, and automatically every five minutes or when idling down after 10–20 minutes, it commits its progress as a checkpoint to a branch on its isolated fork. Nothing touches your main repository until you fetch the branch in muxcode, inspect the diff, and click **Apply changes** (which verifies neither your local branch nor the task branch moved since you reviewed it).
